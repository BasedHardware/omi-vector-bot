# Keep identifying support details private

## Customer failure and boundary

The earlier draft relied on a model instruction and ambiguous staff-card guidance. Instructions do not prevent a model from requesting identifying details publicly or repeating a value already supplied. Aryan authorized one deterministic rework of #84, without another paid comparison.

`publicReplyPrivacy` is the shared public-output boundary used by reviewed presentation, `escalateReply`, the final customer send and customer-visible handoff naming. It removes identifying intake using request verbs (including confirmation), noun questions and sensitive nouns rather than one evaluation phrase or product URL. It preserves non-sensitive diagnostics, negative warnings, appropriately masked screenshot requests and safe official links. A hidden screenshot field does not exempt another readable field or a separately requested secret. Compound declarations are parsed field by field; short/grouped/multiword known private values and non-public tracking links are removed from echoes, including a copied topic. Protected link placeholders are excluded from value substitution. Official-host URL fragments cannot shield an identifier. Only the existing public support aliases—not every address on the product domain—are exempted from email redaction.

The filter returns an in-process intake-needed flag. This survives later canned/planned reply replacements and delivery handling; it is not retained in a database or sent as a new model instruction. Source-only/empty output cannot count as a solved request. The existing safe fallback and handoff decision remain available.

## Application-owned next step

After filtering, append at most one localized private next step:

- `/order` only when the existing order flow reports live (Shopify, binding/encryption and verification email configured).
- Otherwise, a private staff follow-up line only after application-confirmed staff delivery. This is not acceptance, resolution or a promised deadline.
- Otherwise, no private-path claim. Existing honest failed-delivery fallback remains available.

No generated DM/contact alternative may replace a removed identifying request. A private order flow does not authorize collecting passwords, payment details or verification codes; the staff wording explicitly prohibits those disclosures. Customer-facing copy covers English, German, French, Spanish, Portuguese, Italian, Turkish, Indonesian, Chinese, Japanese and both Hindi scripts, with the existing English unknown-language default.

`fitPublicReply` reserves the complete application-owned recording-custody warning, private next step and scoped handoff link before optional prose, then uses the existing whole-unit/source-preserving clipper. Ordinary unchanged replies retain their previous presentation/clipping behavior. Only the actual application's allowed handoff channel IDs survive the public identifier redaction.

Staff-card guidance identifies what may be relevant for private review but does not tell staff to collect identifying details in the thread: the application provides the private path. Missing device/app/OS details and safe damage evidence remain useful. One short model rule remains in answer/review; the planner injection is removed. No new private command, storage, authorization, provider call, training import, optional enablement or #82 contract is introduced.

## Verification and limits

- The initial32 output regressions fail before implementation, not merely because a prompt lacks words. Additional observed-red tests cover indirect intake, compound echoes, URL wrappers/fragments, invented private routes, safe-warning preservation and handoff titles.
- Real-handler fixtures cover ordinary/removed-only output, confirmed and failed staff delivery, configured command availability, long final replies and secret-free generated thread names. They exercise production handler/formatting code with synthetic transports, not live provider quality or GitHub publication permission.
- Existing source/clipping, staff audience, handoff, runtime, memory-isolation and SQL checks remain required. Full/offline/current-head CI and independent final review must pass before readiness. Local and hosted evidence is recorded in the implementation checklist/PR; no test failure is waived as a rerun.
- Independent preliminary review found concrete echo/URL/request/preservation gaps, including overbroad masked-evidence exceptions, conjunction capture and placeholder corruption. Each has an observed-red regression and is being independently rechecked before approval. The draft is not approved or deployed merely because targeted tests pass.

This is deterministic enforcement for the supported request patterns and identifiable supplied values, not a universal personal-data recognizer or proof every possible secret can be inferred from unlabeled text.
